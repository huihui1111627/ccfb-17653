# 键值库 fork()/Copy-On-Write 内存与延迟仿真

模拟 Redis 类内存键值库在 **fork 持久化（RDB/AOF rewrite）** 期间的真实操作系统行为：
父子进程共享内存页，父进程一写某页，内核就复制整页（Copy-On-Write）。
用纯 Python + NumPy 复现「数据只占一半内存、做快照却冲到 60GiB 被杀」的现象，并量化
写入速率、写入分布、快照耗时、透明大页（THP）对**峰值内存**和**高分位延迟**的影响。

## 核心结论（先看这个）

对 30 GiB 数据 / 64 GiB 机器、4000 写/秒、180 秒快照的同口径推演：

| 配置 | 写入模式 | 峰值内存 | COW 复制 | 真正撞缺页的请求 | p99 延迟 | 结果 |
|---|---|---:|---:|---:|---:|---|
| **THP 开（2MiB 大页）** | 均匀随机 | **71.7 GiB** | 35.8 GiB | 7.4% | **9.4 ms** | **OOM 被杀** |
| THP 开 | 热键反复 | 71.6 GiB | 35.8 GiB | 5.7% | 9.2 ms | OOM 被杀 |
| THP 开 | 大键+小键 | 71.7 GiB | 35.8 GiB | 7.4% | 9.5 ms | OOM 被杀 |
| THP 开 | 顺序导入 | 38.2 GiB | 2.4 GiB | 0.2% | 0.84 ms | 存活 |
| **THP 关（4KiB 基础页）** | 均匀随机 | 38.5 GiB | 2.6 GiB | 96.3% | 0.85 ms | 存活 |
| THP 关 | 大键+小键 | 41.4 GiB | 5.6 GiB | 100% | 0.88 ms | 存活 |

**根因（注意一个反直觉的点）**：透明大页把单次复制单位从 4 KiB 放大到 2 MiB（512 倍）。
随机小键写在快照窗口内会把几乎所有大页逐个复制一遍，父进程 footprint = 原数据 + 全量大页
副本，直接打满物理内存。

延迟的来源和直觉相反，必须分清两件事：
- **THP 关**：容器是几百万个 4K 页，快照期内 96% 的写请求都会撞缺页——但每次只复制 4 KiB、
  停顿约 8 µs，**又多又便宜**，p99 始终平稳在亚毫秒。
- **THP 开**：容器只有约 1.8 万个 2M 大页，每个大页只故障一次，所以真正撞缺页的请求只有 7%；
  但每次复制 2 MiB、停顿约 150 µs，更致命的是全量大页副本把内存推到 98%+，
  **OOM 前的内存压力（回收/换页停顿）把 p99 抬到 9 ms 级**——又少又贵，还引爆 OOM。

所以高尾延迟的主因不是「每个请求都在复制页」，而是「复制单位太大导致内存打满后的系统性压力」。
开发说的「写得多」是触发条件，运维说的「快照慢」给了复制足够时间，**真正的放大器是 THP**。

运维把数据压到 20 GiB 之所以有效：网格推演显示 THP 开启时 **20 GiB 是安全线、30/40 GiB 大面积
OOM**；但这是 THP 开启下的自保值，关掉 THP 后 35 GiB（55% 内存）仍安全，不用浪费一半内存。

## 关键机制与建模

### 1. 键值如何落到内存页（pages.py）
- 小键值共享同一基础页（4 KiB），大键值跨多个连续页；
- 删除/过期只把字节还给分配器，物理页不立即归还，留下**空洞页**——
  它仍处于已映射状态，fork 后被写一样会被复制；
- `PageArena` 是 O(页数) 的统计模型，可直接建 30 GiB 场景（约 900 万 4K 页）；
  `KeySpace` 是逐键精确模型，用于小场景验证落页规则。

### 2. 复制页随时间增长（engine.py + analytic.py）
均匀随机写服从优惠券收集模型，被复制页数期望
`C(t) = N·(1 − e^(−w·q/N))`，w=累计写次数、q=每次写平均碰页数、N=已映射页数。
关键在「容器数 N」：THP 关时 N 是几百万个 4K 页，THP 开时 N 缩成约 1.8 万个 2M 大页，
饱和时间随之缩短约 512 倍（同口径 30GiB/4000wps：复制 50% 容器，THP 关需 ~27 分钟、
THP 开仅 ~3.2 秒）。仿真与闭式公式在 192 组网格上误差中位数约 3.7%。

### 3. 透明大页（THP）
开启后复制单位变为 2 MiB（=512 个 4K 页，注意不是 2 GiB）。随机写触碰大页内任意字节，
整个大页都被复制。`expand_to_huge()` 把基础页脏集合向量化展开到大页全量页。

### 4. 缺页停顿与高分位延迟
请求延迟 = 对数正态基础延迟 + 首次写页的缺页复制停顿（4K≈8µs / 2M≈150µs）+ 内存压力停顿。
缺页概率在**复制容器层面**计算（一个大页只故障一次），不是按基础页数——否则 THP 下会
错误地得到「每个请求都缺页」。已复制过的容器再次写不再停顿，所以热键/随机写的故障率随
快照推进衰减。当 footprint 超过物理内存 80%，内存压力停顿线性增大，这是 OOM 场景
高尾延迟（p99 数毫秒）的主要来源。

### 5. 真实 fork 实测（real_fork.py）
`os.fork()` 派生子进程持有同一 mmap，父进程按三种模式写。
复制页数用 `getrusage(RUSAGE_SELF).ru_minflt` 的**次缺页差值**做内核级精确计数
（macOS 内存压缩会让 RSS/footprint 差值严重失真，故不采用）。
本机（arm64，16 KiB 页）实测：**缺页写比普通写慢 13~25 倍**，仿真与实测页号序列对齐后页数误差 0%。
> macOS 无用户态 THP，大页影响只在仿真中验证；基础页 COW 规律两平台一致。

## 五条建议（详见看板 ⑦，均附推演数字）

1. **快照放写入低谷**，最好拆到从节点做（主库零 COW）；速率减半，复制量近半。
2. **关闭 THP**（`echo madvise > /sys/kernel/mm/transparent_hugepage/enabled` 或 never）。
3. **容量**：关 THP 后可放到物理内存 65~70%，不必压到 30%。
4. **批量导入/大键写避开快照窗口，大键拆小**；顺序写复制曲线最陡。
5. **定期低峰 rewrite 治理空洞**；fill_fraction 每低 10%，同等写入复制量等比放大。

## 标定参数说明
延迟模型默认值（8µs/4K 缺页、150µs/2M 大页缺页、fork 10ms/GiB）取 Linux 实测量级；
本机实测值会回标到对应档位。所有参数集中在 `engine.py:LatencyModel`，可按你的机器调整。
